# Ferrowarden 0.2.0

> This release widens credential coverage with field placeholders, makes agent keys default-deny and scoped, adds an optional admin web UI, and records security events in a stable format for your SIEM. Review the upgrade notes and security changes before deployment: the default vault backend changes (the `bw-serve` container is gone from the default stack), and keys created with 0.1.0 become deny-all until you set a policy.

Ferrowarden is a source-available credential proxy that runs alongside [Vaultwarden](https://github.com/dani-garcia/vaultwarden). Agents send requests with `{{vault:name}}` placeholders; Ferrowarden resolves the credentials, forwards the request, and scrubs known credential values from the response. It is a sidecar to Vaultwarden, not a fork or replacement, and is not affiliated with Vaultwarden or Bitwarden.

## Highlights

### Native vault backend (the default)

- Ferrowarden reads the vault itself, over the Bitwarden client protocol, instead of through `bw serve`. **No decrypted values cross a network:** the vault is held as ciphertext and only the requested field is decrypted, per request, into a buffer that is wiped afterwards.
- One fewer container, and no Node.js or Bitwarden CLI in the deployment. Even the one-shot that makes Vaultwarden's internal certificate is now `ferrowarden internal-certs`, the same Rust binary: no Node.js, no shell and no openssl anywhere in the default stack. `bw-serve` is deprecated and removed in the next release; for now `docker-compose.bw-serve.yml` keeps it available. See [docs/native-vault.md](../native-vault.md) and the upgrade note below: this is a breaking change for 0.1.0 deployments.
- Items whose collection hides passwords from your account are left out unless you opt in with `vault.allow_hidden_passwords`.

### Credential coverage

- **Field placeholders**: `{{vault:NAME:username}}`, `:totp`, `:notes` and `:field:FIELD` for custom fields. Secure notes are supported, and item or field names with spaces or colons use single quotes, e.g. `{{vault:'Proxmox (prod)':field:'api secret'}}`.
- `GET /v1/credentials?detail=true` returns ready-made placeholders, unavailable values with the reason, and each credential's `bound_to` hosts.
- The reserved custom field `ferrowarden_uris` sets an item's host bindings, which secure notes need.

### Scoped, default-deny agent keys

- Every agent key carries a policy: `credentials` (name patterns) and `methods` (HTTP methods). Anything not allowed is refused with `403` before any vault access or outbound connection.
- `PATCH /v1/admin/keys/{id}` changes a policy; `POST /v1/admin/keys/{id}/preview` shows what a draft policy would allow, without saving or sending anything.
- Request bodies and the key file are parsed strictly: duplicate keys, unknown fields, trailing data and ambiguous headers are rejected.

### Admin web UI (optional)

- A separate listener, off unless `ui.bind` is set. Sign in with your Vaultwarden master password, verified by Vaultwarden itself, including two-step login.
- Manage keys and policies, use **Check policy** before saving, and browse the audit view. See [docs/admin-ui.md](../admin-ui.md) for deployment guidance and the residual risks.

### Security events

- One structured event, with a documented schema, for every security-relevant action, and a request ID on every response.
- Sinks: stdout, a rotating file, and syslog over UDP, TCP or TLS. Loki and Wazuh examples are in [examples/siem](../../examples/siem/README.md). See [docs/events.md](../events.md).

### Brand and command line

- New Ferrowarden identity: logo, README and docs headers, and a redesigned admin UI.
- `ferrowarden --help` and `--version`.

## Security notes

Ferrowarden narrows how credentials are exposed to agents; it does not remove every risk. Scrubbing has limits, a credential sent to a host it is bound to is in that host's hands, and a compromised Ferrowarden host exposes credentials. Read [docs/security.md](../security.md) for the threat model and limits. To report a vulnerability, follow the [Security Policy](../../SECURITY.md).

## Upgrading

- **The internal CA is reused; nothing to do.** The `internal-certs` one-shot now runs the Ferrowarden image instead of a Node-based one. It keeps your existing CA (including one made by the old openssl script), leaves a valid Vaultwarden certificate alone, and signs a new one under the same CA when it must. Trust you already gave `ca.crt` stays valid. `docker compose up -d --build` is all it takes. A misspelled entry in `VAULTWARDEN_CERT_SANS` is now an error that names it, instead of being passed on unchecked.
- **Breaking: Ferrowarden now reads the vault itself, and `bw-serve` is gone from the default stack.** The native vault backend is the default (`vault.backend = "native"`). The `bw-serve` service and the `bw-data` volume are no longer in `docker-compose.yml`. `bw-serve` is **deprecated**: it stays available for this release (see step 5) and is removed in the next. For a 0.1.0 deployment, step by step:

  1. **Pull the new Compose file and restart.** `git pull`, then `docker compose up -d --build`. Add `--remove-orphans` to remove the old `bw-serve` container. If you maintain your own Compose file, copy these lines from the new `docker-compose.yml` into the `ferrowarden` service: the `bw_client_id` and `bw_client_secret` entries under `secrets:`, `FERROWARDEN_VAULT__URL`, `FERROWARDEN_VAULT__CA_FILE`, `FERROWARDEN_VAULT_CLIENT_ID_FILE`, `FERROWARDEN_VAULT_CLIENT_SECRET_FILE`, and replace the `bw-serve` entry under `depends_on:` with `vaultwarden`. Drop `FERROWARDEN_BW_SERVE_URL`.
  2. **Your secrets stay the same, and Ferrowarden now reads all of them.** `secrets/bw_client_id` and `secrets/bw_client_secret` (your Vaultwarden personal API key) used to be read by the `bw-serve` container; Ferrowarden reads them now, as `FERROWARDEN_VAULT_CLIENT_ID_FILE=/run/secrets/bw_client_id` and `FERROWARDEN_VAULT_CLIENT_SECRET_FILE=/run/secrets/bw_client_secret`. `secrets/bw_master_password` (`FERROWARDEN_UNLOCK_FILE`) and `secrets/ferrowarden_admin_key` are unchanged. **On Linux, give Ferrowarden's user (UID 999) the two API key files:** `sudo chown 999:999 secrets/bw_client_id secrets/bw_client_secret`. They were owned by UID 1000 for `bw-serve`, and Ferrowarden will not start if it cannot read them.
  3. **Set `vault.url` if you are not using the bundled Compose file.** The default is `https://vaultwarden`, the bundled service name. Point `FERROWARDEN_VAULT__URL` (or `vault.url`) at your Vaultwarden over `https://`, and `FERROWARDEN_VAULT__CA_FILE` (`vault.ca_file`) at its CA certificate if it is not publicly trusted. If the API key or `vault.url` is missing, Ferrowarden stops at startup with a message that names the settings and points to `docs/native-vault.md`.
  4. **Check it worked, then clean up.** `GET /v1/admin/status` should report `"vault_backend": "native"` and the same `credential_count` as before. Once it does, the `bw-data` volume is unused. It holds only the Bitwarden CLI's login state and a cache, never your vault, so removing it is safe: `docker volume rm <project>_bw-data` (list yours with `docker volume ls`; the project name is your Compose directory name by default). **Be careful to name `bw-data`: `vaultwarden-data` holds your vault.** You can leave `bw-data` in place for now.
  5. **To stay on bw-serve for this release**, add the override file: `docker compose -f docker-compose.yml -f docker-compose.bw-serve.yml up -d`. Outside Compose, set `vault.backend = "bw-serve"` (`FERROWARDEN_VAULT__BACKEND=bw-serve`) and keep `bw_serve_url`. Ferrowarden logs a deprecation warning at every start. The override file and the backend are removed in the next release, so plan the move to native.
  6. **Items whose collection hides passwords are now left out.** The native backend does not offer an organisation item that Vaultwarden marks "Hide passwords" for your account, because Ferrowarden would otherwise hand that password to an agent. It is counted in the `vault_sync` event under `hidden_password`. If you rely on such items, `vault.allow_hidden_passwords = true` brings them back. See [docs/native-vault.md](../native-vault.md#hidden-passwords-collections-that-hide-them).
  7. **File unlock mode has a trade-off to know about.** With `unlock_mode = "file"`, one process now holds both the API key and the master password. `unlock_mode = "manual"` is the hardened option: type the password after each restart and remove the `bw_master_password` secret. See [docs/security.md](../security.md#native-backend-one-process-holds-both-secrets).
- **Admin UI (optional):** nothing changes unless you set `FERROWARDEN_UI__BIND`. The Docker image now needs the `templates/` directory when built from source (the `Dockerfile` copies it). Run `docker compose up -d --build` so `internal-certs` fills the new `internal-ca-public` volume. Keep the UI port off agent-reachable networks and serve it over HTTPS (see `docs/admin-ui.md`).
- **Agent keys now require an explicit policy, and keys created with 0.1.0 become deny-all.** `POST /v1/admin/keys` now requires `credentials` and `methods` (`["*"]` for everything, `[]` for nothing; omitting them or sending `null` is a `400`). Keys already in your key file have no policy: after the upgrade they authenticate but can list no credentials and forward nothing until you set one. They are shown with `"policy_set": false` in `GET /v1/admin/keys`, counted in the `startup` event (`keys_without_policy`), and a warning is logged at startup. To restore the previous behaviour for a key, run:

  ```sh
  curl -X PATCH https://<host>:3000/v1/admin/keys/<key-id> \
    -H "X-Admin-Key: $ADMIN_KEY" -H "Content-Type: application/json" \
    -d '{"credentials":["*"],"methods":["*"]}'
  ```

  (set both fields; a field you leave out stays deny-all on such a key). Better, scope each key to what its agent needs. Scripts that create keys must send a policy. A key file with `null` policy values fails to load at startup.
- **`/v1/forward` now rejects methods outside `GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS`** (for example `TRACE` or `CONNECT`) with `400`, for every key. The method is matched case-insensitively.
- **Key list output now includes policy fields** (`credentials`, `methods`, `policy_set`), and so do the create and patch responses. Unrestricted is shown as `["*"]`, never `null`.
- **`GET /v1/admin/audit` returns security events instead of the old audit entries.** The fields changed: `timestamp` is now `@timestamp`, `agent_id`/`agent_name` are `ferrowarden.key.id`/`.name`, `method` and `target_url` are `http.request.method` and `url.original`, `credential_names` is `ferrowarden.credentials`, `response_status` is `http.response.status_code` (now a number; it was the string `"Some(200)"`), and `outcome` is `event.outcome` (`success`/`failure`) with the cause in `event.reason`. The ring buffer now also contains non-forward events (authentication failures, key changes, vault events), so filter on `event.action == "forward"` for the old view.
- **The `audit` log line is gone.** The `tracing` line with `message: "audit"` (fields `agent_id`, `credential_names`, `outcome`, ...) is replaced by security events on stdout with a different shape (`event.dataset == "ferrowarden.security"`). Update Loki queries and Wazuh decoders that matched `message="audit"`; see `docs/events.md` and `docs/logging.md`.
- **Authentication is now checked before request bodies are parsed.** An unauthenticated request with a malformed body gets `401` (it used to get a `400` with parse details). Authenticated requests are unaffected.
- **The `api_prefix` value is no longer written to the startup log.** The startup log says only that a prefix is configured.
- **Ferrowarden now shuts down gracefully** on SIGTERM and Ctrl-C (in-flight requests get up to 10 seconds) and flushes the event sinks before exiting.
- **Items with master password re-prompt are now refused (`403`).** Previously they were usable. Turn re-prompt off on items agents should use.
- **URIs with match type *regex* or *never* no longer act as host bindings.** Add a normal URI (or a `ferrowarden_uris` field) if a credential relied on one.
- **Stricter request parsing.** Requests with unknown fields, duplicate JSON keys, case-insensitively duplicated header names, or unknown/repeated query parameters on `/v1/credentials` now get `400`. A key file with duplicate keys or unknown fields fails to load at startup.

Full list of changes: [CHANGELOG.md](../../CHANGELOG.md).
