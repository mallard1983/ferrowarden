# Changelog

All notable changes to this project are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project follows [Semantic Versioning](https://semver.org/). While the version is 0.x, minor releases may contain breaking changes; they are called out under **Upgrading**.

## [Unreleased]

### Added

- **Captured sessions** (#15): a login request can ask Ferrowarden to keep the token it returns, so the agent never sees it. `POST /v1/forward` takes an optional `capture` list (1 to 8 entries of `{ "from": "json:/pointer" | "header:Name" | "cookie:name", "as": "name", "ttl_secs": n }`, strict JSON like the rest of the body, validated before anything is sent). The value is read from the raw response, kept in memory under (agent key, name) and bound to the origin of the login request, and replaced with `[CAPTURED:name]` in the response; the response gains a `captures` list with the status of each entry (`captured`, `not_found`, `not_a_string`, `ambiguous`, `too_short`, `too_long`, `expired`, `limit_reached`). Later requests write `{{session:name}}` in the URL, headers or body; it is substituted only for the same scheme, host and port, and only for the key that captured it. Every session value of a key is scrubbed from every response of that key, whether or not the request used it. A session expires at the earliest of its TTL, the JWT's `exp` and the cookie's `Max-Age`/`Expires`; it ends when the key is revoked or its policy changes, when the vault locks, on `DELETE /v1/sessions/{name}`, and on restart (nothing is written to disk). New: `GET /v1/sessions` and `DELETE /v1/sessions/{name}` (agent key; names, hosts and expiry, never values); the `sessions` settings (`sessions.enabled`, `default_ttl_secs`, `max_ttl_secs`, `max_per_key`, `FERROWARDEN_SESSIONS__*`); the security events `session_capture`, `session_use`, `session_expire` and `session_delete`, and `ferrowarden.sessions` on `forward` events; the reason codes `unknown_session`, `session_host_not_allowed`, `sessions_disabled` and `capture_failed`; the metrics `ferrowarden_session_captures_total`, `ferrowarden_session_uses_total` and `ferrowarden_sessions_active`; `capture` on the MCP `http_request` tool; and the OpenAPI additions. There is no key-policy field for sessions yet: a key that may call a login endpoint may capture, and `sessions.enabled = false` turns the feature off. See [docs/sessions.md](docs/sessions.md), including what it does not protect against (the agent still drives the session while it lives, and a value the target returns in a form the scrubber does not know is not hidden).

### Removed

- **The `bw-serve` vault backend** (#48), deprecated in 0.2.0: the `bw serve` client, `vault.backend = "bw-serve"`, the `bw_serve_url` setting (`FERROWARDEN_BW_SERVE_URL`), the deprecation warning, `docker-compose.bw-serve.yml` and the `bw_serve_locked` lock cause. Nothing in the project or its CI runs Node.js or the Bitwarden CLI as part of Ferrowarden any more; the native backend is the only vault backend. The internal `Vault` interface stays so that another backend can be added later.

### Changed

- **Breaking: `vault.backend = "bw-serve"` (in `ferrowarden.toml` or as `FERROWARDEN_VAULT__BACKEND=bw-serve`) is now a startup error**, not a silent fallback. The message says the backend was removed in 0.3.0 and points to [docs/native-vault.md](docs/native-vault.md#upgrading-from-bw-serve). `vault.backend` accepts `native` only (a config that sets it explicitly keeps working). A leftover `bw_serve_url` or `FERROWARDEN_BW_SERVE_URL` is ignored, with a warning. **Upgrading:** if you were on `bw-serve` in 0.2.0, first follow the 0.2.0 upgrade steps (remove the override file, `chown 999:999` the API key files, set `vault.url` if you run outside the bundled Compose file), then upgrade, and remove the unused `bw-data` volume with the same care as before (`vaultwarden-data` holds your vault).
- `vault_backend` in `GET /v1/admin/status`, the `startup` event, `ferrowarden_build_info` and the admin UI is always `native`. The field stays so that dashboards and SIEM rules keep working.
- The error for an unreachable vault no longer says "bw serve" (`Vault backend is unreachable`), and the help text of `ferrowarden_vault_excluded_items` no longer mentions `bw serve`.

### Internal

- The test stack runs one Ferrowarden, the native one, as `ferrowarden` on port 3000 (UI 3001, metrics 9095). `ferrowarden-native` (3003, 3004, 9096), the `bw-serve` service, `.env.test.native` and the Bitwarden CLI pairing (`BW_CLI_VERSION`) are gone; `docker/bw-cli.Dockerfile` is now `docker/setup.Dockerfile`, a pinned `node:*-slim` for the one-shot setup and seed containers only (no Bitwarden CLI; the `bw_client_id`, `bw_client_secret` and `bw_master_password` secret names are unchanged). CI runs the integration suite once per Vaultwarden version, with the same job names.
- `tests/equivalence.rs` is removed with the backend it compared against. Its coverage is kept as native-only integration tests that derive the expected listing and every expected value from `tests/seed/*.json`: `test_listing_matches_the_seed_data` and `test_every_offered_placeholder_delivers_the_seeded_value`. See [docs/native-vault.md](docs/native-vault.md#how-formats-are-verified) for what vouches for the formats now.
- Unit tests that built an `AppState` with the `bw-serve` backend (because it needed no credentials) use an in-memory `Vault` that exists only in the test build.

## [0.2.0] — 2026-11-25

> This release reads the vault natively, with no `bw serve`, Node.js or openssl in the default deployment, ships a hardened shell-less container, widens credential coverage with field placeholders, makes agent keys default-deny and scoped, adds an optional admin web UI, records security events in a stable format for your SIEM, and adds push notifications, Prometheus metrics, an MCP server and an OpenAPI specification. Review the upgrade notes and security changes before deployment: the default vault backend changes (the `bw-serve` container is gone from the default stack), and keys created with 0.1.0 become deny-all until you set a policy.

### Added

- **`ferrowarden internal-certs`**: a subcommand that creates and renews the internal CA and Vaultwarden's certificate, replacing `docker/gen-internal-certs.sh`. It reads the same settings (`PKI_DIR`, `CA_PUBLIC_DIR`, `VW_HOSTNAME`, `VW_EXTRA_SANS`, which it now validates), writes the same files with the same names, modes and renewal rules, and publishes only `ca.crt`. It uses rcgen (ring backend) to issue certificates and rustls-webpki to decide whether an existing one is still good. See [docs/tls.md](docs/tls.md#the-internal-ca-how-it-is-made).
- **Prometheus metrics** (#13): an optional `/metrics` endpoint for request volume, outcomes, latency, response sizes, rate limiting, authentication failures, vault state (locked, credential count, last sync, items left out), agent keys without a policy, notifications and dropped events, with a **Grafana dashboard** (`examples/grafana`) and a Prometheus scrape configuration (`examples/prometheus`). **Off by default**; enabled with `metrics.bind` (`FERROWARDEN_METRICS__BIND`) on a **separate listener** that serves `GET /metrics` only and is never part of the API or UI. **A bearer token is required by default** (`FERROWARDEN_METRICS_TOKEN` or `_FILE`, compared in constant time, never logged); a non-loopback bind without one is refused at start unless `metrics.allow_unauthenticated = true`. With `tls_enabled` the listener serves TLS with the same certificate. Counters and histograms are fed by the security event stream through its own bounded queue (`emit` can never wait for metrics); gauges are read from the live state at scrape time. Label values come only from fixed enums and from agent key names; nothing from a request (URL, host, IP, header name, placeholder, value) can become a label, which tests check with hostile events, real traffic on both backends and the CI secret gate. Credential names are labels only with `metrics.credential_labels = true` (`ferrowarden_forward_credential_uses_total`, capped at 500 names, successful forwards only). OpenMetrics text format via the `prometheus-client` crate (0.26, Apache-2.0 OR MIT; its dependencies `dtoa`, `itoa` and `parking_lot` are MIT or Apache-2.0). Event `metrics_auth` (failed scrapes, at most one per source address per minute) with reasons `missing_metrics_token` and `invalid_metrics_token`; the `startup` event reports `metrics_enabled`, `metrics_auth`, `metrics_tls` and `metrics_credential_labels`; the `forward` event gains `http.response.body.bytes` (the size of the target's response, never its content). See `docs/metrics.md`.
- Test stack: both Ferrowarden instances run the metrics listener (ports 9095 and 9096) with a token from `secrets/metrics_token`, which `scripts/dev-setup.*` generate; the integration suite checks the token, the 404 and 405 rules, the series after real traffic and that a scrape holds no secret value, token, vault item name, host, URL or IP; `scripts/check-no-secrets.sh` scans a scrape of each instance.
- **Native vault backend** (#36), the new default (see Changed): `vault.backend = "native"` (`FERROWARDEN_VAULT__BACKEND`) makes Ferrowarden read the vault itself instead of through `bw serve`: the Bitwarden client protocol and cryptography implemented in Rust directly against Vaultwarden, with no `bw` CLI, no Node.js and no Bitwarden SDK code (implemented from the observed wire format and the published algorithms; the SDK's licences are incompatible with Ferrowarden's). **It is the default as of this release**, and `bw-serve` is deprecated. The vault is held as ciphertext, only names, URIs and field names are decrypted at sync, and a secret is decrypted for one request into a wiped buffer, so nothing decrypted crosses a network and the whole-item fetch is gone. Strict EncString allow-list (AES-256-CBC with HMAC-SHA256, MAC verified in constant time before decrypting; RSA-OAEP only for RSA keys; type 0 and everything else refused), exact 64-byte keys, per-item keys, organisation items, and **fail closed per item**: an unreadable item is left out and counted by reason in the `vault_sync` event (`excluded`, `excluded_reasons`, `excluded_ids`). The refresher logs in again before the token expires, polls the account revision and syncs only on change (plus a periodic safety sync); a changed user key or security stamp locks the vault. On Linux the process disables core dumps (`PR_SET_DUMPABLE`, `RLIMIT_CORE`). New dependencies, all MIT OR Apache-2.0 and pure Rust: `aes`, `cbc`, `hkdf`, `rsa` (0.10 or later: RUSTSEC-2023-0071 is fixed there), `sha1`, and `libc` on Linux. In file unlock mode one process holds both the API key and the master password; manual mode is the hardened option ([security.md](docs/security.md#18-the-native-vault-backend)). See `docs/native-vault.md`.
- **Equivalence suite for the two backends**: the test stack runs two Ferrowarden instances against one Vaultwarden account, `ferrowarden` (bw serve, port 3000) and `ferrowarden-native` (port 3003, UI 3004), and `tests/equivalence.rs` proves that the detailed credential listing is identical and that every offered placeholder, and a set of bad ones, substitutes the same value or fails the same way through both. CI also runs the whole integration suite against the native instance. CI runs it all against two Vaultwarden releases (see Changed). `VAULTWARDEN_VERSION` selects the Vaultwarden release of the test stack.
- Test fixtures: `docker/bw-seed.js` no longer needs the `bw` CLI to describe its data and now seeds items with per-item keys, an organisation with a collection and its items, card, identity and SSH items, an archived item, URI match types, a custom-field mix, TOTP as otpauth (SHA-256, 8 digits, 60 s), Steam and a bare secret, and edge cases (blank password, empty-string username, no URIs, Unicode, very long values). Known-answer vectors for the cryptography are generated with Node's `crypto` (`tests/native-vectors/gen.js`).
- `vault.url` and `vault.ca_file` (`FERROWARDEN_VAULT__URL`, `FERROWARDEN_VAULT__CA_FILE`): one setting for how Ferrowarden reaches Vaultwarden. `ui.vaultwarden_url` and `ui.vaultwarden_ca_file` still work as **deprecated aliases** (a warning is logged). `FERROWARDEN_VAULT_CLIENT_ID[_FILE]` and `FERROWARDEN_VAULT_CLIENT_SECRET[_FILE]` hold the API key for the native backend.
- `GET /v1/admin/status` reports `vault_backend`; so do the `startup` event (`vault_backend`) and the admin UI status page. New `vault_lock` causes with the native backend: `vault_locked`, `security_stamp_changed`, `vault_key_changed`.
- `scripts/check-no-secrets.sh` scans both Ferrowarden instances (and the Vaultwarden API key); `scripts/dev-setup.*` start both and write `.env.test.native`.
- **Push notifications for security events** (#12): Ferrowarden can tell you about blocked requests, repeated authentication failures, vault lock and unlock failures, and (opt-in) key and sign-in changes, through **Gotify**, **ntfy** and a **generic webhook** (Matrix, Slack, Discord and similar through their webhook bridges; no native support is claimed). The notifier is another consumer of the security event stream with its own bounded queue and one worker per sender, so a slow or broken notifier never delays a request, an event or another sink; what does not fit is counted and reported in the next notification. Categories `blocked`, `auth_failure`, `vault`, `admin` and `system` (default: all but `admin`); failures are counted per source IP (5 in 5 minutes by default, across agent, admin and UI); at most one notification per category and subject per minute with an "and N more since HH:MM" summary; at most 60 an hour, then one "paused" notice. A notification is built only from an allow-list of event fields (credential names, target host, key name and short id, source IP, request id, reason code, counts) in code that is table-tested against hostile events: never values, tokens, URL paths or queries, header names or values, bodies, the API prefix or Vaultwarden messages. Configured under `[notify]` / `FERROWARDEN_NOTIFY__*`; tokens only from `FERROWARDEN_NOTIFY_{GOTIFY,NTFY,WEBHOOK}_TOKEN` or `_FILE` (both set is an error), held in wiped memory and never logged; `https://` required except loopback or `allow_http`; no redirects, 10 second timeout, two retries on network errors and 5xx. The notifier hosts are on a deny list in the outbound target policy, so an agent cannot forward to them (`403`, `target_blocked`). See `docs/notifications.md`.
- **`POST /v1/admin/notify/test`** (`sendTestNotification`) sends a test notification to every enabled sender and reports each result (`sender`, `ok`, `status`, `error` without URLs or tokens); one per 10 seconds on top of the admin rate limit. The admin UI status page gains a **Notifications** section (senders by type and host, categories, counters) and a **Send test notification** button. Event `notify_test`; the `startup` event reports `notify_senders` and `notify_allow_http`.
- Test stack: the mock API answers to a second network alias, `notify-sink`, and keeps requests made under that name in a separate log (`/__notifications__`); `scripts/dev-setup.*` generate `secrets/notify_webhook_token`, which `scripts/check-no-secrets.sh` includes in its list of secrets.
- **MCP server** (#11): `ferrowarden-mcp`, a second binary in the crate that exposes Ferrowarden to MCP-capable agent harnesses over stdio. Two tools, `list_credentials` and `http_request`, with strict input schemas (checked in a test against `docs/openapi.yaml`) and tool descriptions that carry the key rules. It is a thin client of a running Ferrowarden holding only an agent key: configured with `FERROWARDEN_URL` (including any `api_prefix`), `FERROWARDEN_AGENT_KEY` or `FERROWARDEN_AGENT_KEY_FILE`, and optionally `FERROWARDEN_CA_FILE`, `FERROWARDEN_MCP_TIMEOUT_SECS`, `FERROWARDEN_MCP_ALLOW_HTTP` and `FERROWARDEN_MCP_LOG`. HTTPS is required except for loopback hosts. The key and the URL path are never logged or shown in tool output; stdout carries only protocol messages. Errors from Ferrowarden itself become tool errors with guidance per status, distinct from a target's own 4xx and 5xx. Uses the official `rmcp` SDK. See `docs/mcp.md`, with configuration for Claude Code, Claude Desktop and generic stdio clients.
- **Release workflow** (`.github/workflows/release.yml`): for a `v*` tag, builds `ferrowarden` and `ferrowarden-mcp` for Linux (x86_64, aarch64), macOS (Apple silicon) and Windows (x86_64), writes `SHA256SUMS`, attests build provenance and attaches the files to a draft release, which is never published automatically. A manual run is a dry run that cannot upload.
- **OpenAPI specification** (#10): `docs/openapi.yaml`, a hand-written OpenAPI 3.1 description of every route (operations, parameters, request bodies, each response status with its schema, the placeholder grammar, scrubbing and its limits, examples, and the security event schema). Each operation has a stable `operationId` (`listCredentials`, `forwardRequest`, `createKey`, ...). It is checked in CI: Redocly lint, a test that the routes the server serves and the spec describe are the same set, and integration tests that validate real responses against the response schemas.
- **`GET /v1/openapi.json`** serves the specification to holders of a key: an agent key gets the agent and meta operations, the admin key gets the full document, and `servers[0].url` is set to the configured `api_prefix`. No key gets `401`. It counts against the agent rate limit. Event `openapi_read` (details `variant`: `agent` or `admin`). The Docker image now copies `docs/openapi.yaml` into the build, because the file is embedded in the binary.
- `docs/integrations/n8n.md`: using Ferrowarden from the n8n HTTP Request node.
- **Ferrowarden brand identity**: logo and brand kit in `branding/` (assets, tokens, voice and messaging guide), README and docs headers, release-notes header, and a redesigned admin web UI using the same palette. README, docs, CLI text and release notes now follow the kit's claims rules: credential protections are described as design properties with their limits, and Ferrowarden is described as a sidecar to Vaultwarden, not affiliated with Vaultwarden or Bitwarden.
- **Admin web UI design**: the brand palette, the self-hosted Inter font (OFL, served from the UI's own origin), the brand mark and lockup, favicons, and light and dark themes that follow the system setting. The layout is responsive: the keys and audit tables become cards on narrow screens, and the filters, key editor and navigation fit phone widths. The UI's Content-Security-Policy adds `font-src 'self'` and is otherwise unchanged (no scripts, no inline styles).
- **Command-line help**: `ferrowarden --help` / `-h` prints usage and where configuration comes from, `--version` / `-V` prints the version, and any other argument exits with status 2 and the usage on stderr. Running with no arguments starts the proxy as before.
- **Admin web UI, phase 2** (#24): `/ui/keys` (list, with a deny-all badge for keys without a policy), `/ui/keys/new` (create; the token is rendered once in the POST response, never in a URL, redirect, event or log), `/ui/keys/{id}` (policy editor with **Check policy** showing gained and lost credentials, placeholders and `bound_to` hosts, a request check, and a confirmation step for changes that widen access), `/ui/keys/{id}/revoke` and `/ui/audit` (filters, strict query, per-event JSON). A 10-minute "sudo" window requires a recent sign-in for create, revoke and save, enforced on both GET and POST, with a strictly validated `next` redirect carried server-side through two-step login. Key operations now live in one shared service (`api::key_service`) used by both the JSON API and the UI. Events from either path carry `details.via` (`api` or `ui`). The create form is single-use, so reloading or re-sending it cannot create a second key. A save or create made after the sign-in window keeps your changes: they are held server-side (15 minutes, tied to your IP) and restored, unsaved, after you sign in again. No JavaScript. See `docs/admin-ui.md`.
- **Admin web UI, phase 1** (#24): an optional operator UI on its own listener (`ui.bind`, off by default; never merged into the API router). Sign in with the Vaultwarden master password, verified by Vaultwarden itself (login hash derived with PBKDF2 or Argon2id, server KDF parameters bounded), including two-step login (authenticator app, email code, YubiKey OTP). Server-side sessions (idle 15 min, 8 h absolute, 8 at most, SHA-256 of the id stored), `__Host-` `HttpOnly` `Secure` `SameSite=Strict` cookies, CSRF token plus same-origin check on every POST, per-IP and global sign-in lockouts checked before any key derivation, strict form parsing, no scripts, strict security headers, and a read-only status page. The sign-in form is only served over HTTPS (own TLS, or a `trusted_proxies` proxy sending `X-Forwarded-Proto: https`); `ui.insecure_http` opts out for local testing. No Vaultwarden token or key is ever read or kept. See `docs/admin-ui.md` and `docs/security.md` §16.
- Events `ui_login`, `ui_logout`, `ui_session_expired`, `ui_two_factor_email_sent`; reasons `invalid_credentials`, `two_factor_required`, `two_factor_failed`, `login_locked_out`, `upstream_rate_limited`, `insecure_transport`; the `startup` event reports `ui_enabled`, `ui_tls`, `ui_insecure_http`. Wazuh rules 100290 to 100293 and a LogQL query in the SIEM examples.
- **`internal-ca-public` volume**: the `internal-certs` one-shot now also copies `ca.crt` (never the key) into it, and `ferrowarden` mounts it read-only at `/ca-public` to verify Vaultwarden's certificate for the UI sign-in. `docker compose up` re-runs the one-shot, so existing deployments get it automatically.

- **Per-agent credential scoping and method policy** (#9): every agent key carries a policy, `credentials` (name patterns, `*` wildcard, whole-name, case-sensitive) and `methods` (`GET HEAD POST PUT PATCH DELETE OPTIONS`). `GET /v1/credentials` lists only matching credentials. `/v1/forward` refuses a disallowed method or an out-of-scope placeholder with `403` before any vault access, target check or connection. An out-of-scope name gives the same response and event whether or not the credential exists, so scoping cannot be used to probe the vault.
- **`PATCH /v1/admin/keys/{id}`** changes a key's policy (absent field = unchanged, `null` and `{}` rejected, takes effect immediately).
- **`POST /v1/admin/keys/{id}/preview`**: shows what a draft policy would allow (credentials reached, access gained and lost against the saved policy, and optionally whether a given request would be allowed), without saving, reading values or sending anything.
- Events `key_policy_change` and `policy_preview`; reasons `credential_out_of_scope` and `method_not_allowed`; `key_create` records the policy; the `startup` event reports `keys_without_policy`. SIEM examples updated.
- **Field placeholders** (#8): `{{vault:NAME:username}}`, `:totp`, `:notes` and `:field:FIELD` for custom fields (text, hidden, boolean, and linked to the username or password). **Secure notes** are now supported.
- **Any item or field name**: names with spaces, colons or other characters are referenced with single quotes, e.g. `{{vault:'Proxmox (prod)':field:'api secret'}}`.
- `GET /v1/credentials?detail=true` returns ready-made placeholders for every available value, unavailable values with the reason, and each credential's `bound_to` hosts.
- Reserved custom field `ferrowarden_uris` sets an item's host bindings (needed for secure notes; overrides a login's URIs).

- **Security event stream** (#22): one structured event, with a stable documented schema (`ferrowarden.schema_version` 1, ECS-style field names), for every security-relevant action: forwards (success and each block reason), failed agent and admin authentication, credential listings, key create/revoke/list, audit and status reads, vault unlock/lock/sync, rate limiting (aggregated), rejected requests, startup, shutdown and dropped events. See `docs/events.md`.
- **Event sinks**, configurable under `[events]` / `FERROWARDEN_EVENTS__*` and combinable: stdout JSON lines (default), a rotating JSON-lines file, and RFC 5424 syslog over UDP, TCP or TLS. Delivery is queued and never blocks or fails a request; overflow is counted and reported as an `events_dropped` event.
- **Request IDs**: every response carries an `X-Request-Id` header (UUID v7, always generated by Ferrowarden), also present in every event for that request. The client IP is now computed once for all consumers.
- `GET /v1/admin/audit` accepts `?limit=` (1 to the buffer size; strict query parsing); the buffer size is configurable (`events.buffer_size`).
- `scripts/check-no-secrets.sh`, run in CI after the integration tests: fails if any seeded secret value, agent key, admin key or master password appears in the container logs or the event file.

### Changed

- **Breaking: Ferrowarden now reads the vault itself, and `bw-serve` is gone from the default stack.** The native vault backend is the default (`vault.backend = "native"`). The `bw-serve` service and the `bw-data` volume are no longer in `docker-compose.yml`. `bw-serve` is **deprecated**: it stays available for this release (see step 5) and is removed in the next. For a 0.1.0 deployment, step by step:

  1. **Pull the new Compose file and restart.** `git pull`, then `docker compose up -d --build`. Add `--remove-orphans` to remove the old `bw-serve` container. If you maintain your own Compose file, copy these lines from the new `docker-compose.yml` into the `ferrowarden` service: the `bw_client_id` and `bw_client_secret` entries under `secrets:`, `FERROWARDEN_VAULT__URL`, `FERROWARDEN_VAULT__CA_FILE`, `FERROWARDEN_VAULT_CLIENT_ID_FILE`, `FERROWARDEN_VAULT_CLIENT_SECRET_FILE`, and replace the `bw-serve` entry under `depends_on:` with `vaultwarden`. Drop `FERROWARDEN_BW_SERVE_URL`.
  2. **Your secrets stay the same, and Ferrowarden now reads all of them.** `secrets/bw_client_id` and `secrets/bw_client_secret` (your Vaultwarden personal API key) used to be read by the `bw-serve` container; Ferrowarden reads them now, as `FERROWARDEN_VAULT_CLIENT_ID_FILE=/run/secrets/bw_client_id` and `FERROWARDEN_VAULT_CLIENT_SECRET_FILE=/run/secrets/bw_client_secret`. `secrets/bw_master_password` (`FERROWARDEN_UNLOCK_FILE`) and `secrets/ferrowarden_admin_key` are unchanged. **On Linux, give Ferrowarden's user (UID 999) the two API key files:** `sudo chown 999:999 secrets/bw_client_id secrets/bw_client_secret`. They were owned by UID 1000 for `bw-serve`, and Ferrowarden will not start if it cannot read them.
  3. **Set `vault.url` if you are not using the bundled Compose file.** The default is `https://vaultwarden`, the bundled service name. Point `FERROWARDEN_VAULT__URL` (or `vault.url`) at your Vaultwarden over `https://`, and `FERROWARDEN_VAULT__CA_FILE` (`vault.ca_file`) at its CA certificate if it is not publicly trusted. If the API key or `vault.url` is missing, Ferrowarden stops at startup with a message that names the settings and points to `docs/native-vault.md`.
  4. **Check it worked, then clean up.** `GET /v1/admin/status` should report `"vault_backend": "native"` and the same `credential_count` as before. Once it does, the `bw-data` volume is unused. It holds only the Bitwarden CLI's login state and a cache, never your vault, so removing it is safe: `docker volume rm <project>_bw-data` (list yours with `docker volume ls`; the project name is your Compose directory name by default). **Be careful to name `bw-data`: `vaultwarden-data` holds your vault.** You can leave `bw-data` in place for now.
  5. **To stay on bw-serve for this release**, add the override file: `docker compose -f docker-compose.yml -f docker-compose.bw-serve.yml up -d`. Outside Compose, set `vault.backend = "bw-serve"` (`FERROWARDEN_VAULT__BACKEND=bw-serve`) and keep `bw_serve_url`. Ferrowarden logs a deprecation warning at every start. The override file and the backend are removed in the next release, so plan the move to native.
  6. **Items whose collection hides passwords are now left out.** The native backend does not offer an organisation item that Vaultwarden marks "Hide passwords" for your account, because Ferrowarden would otherwise hand that password to an agent. It is counted in the `vault_sync` event under `hidden_password`. If you rely on such items, `vault.allow_hidden_passwords = true` brings them back. See [docs/native-vault.md](docs/native-vault.md#hidden-passwords-collections-that-hide-them).
  7. **File unlock mode has a trade-off to know about.** With `unlock_mode = "file"`, one process now holds both the API key and the master password. `unlock_mode = "manual"` is the hardened option: type the password after each restart and remove the `bw_master_password` secret. See [docs/security.md](docs/security.md#native-backend-one-process-holds-both-secrets).

- **Items whose collection hides passwords are left out** (#36): an organisation item the server marks `viewPassword: false` ("Hide passwords" for this account) is no longer offered by the **native** backend: it is not listed, not usable and not in the policy check, and the `vault_sync` event counts it under the reason `hidden_password` (and `ferrowarden_vault_excluded_items` includes it). The new setting `vault.allow_hidden_passwords` (`FERROWARDEN_VAULT__ALLOW_HIDDEN_PASSWORDS`, default `false`) is the opt-in: it logs a warning at startup, and the `startup` event gains `vault_allow_hidden_passwords`. **`bw-serve` is unchanged:** `bw serve` does not report `viewPassword` (so Ferrowarden cannot leave the item out), but the CLI already withholds such a password (`login.password` is `null`, `GET /object/password/<id>` fails), so the item stays listed with its other values and its password is never released; the setting has no effect there (a warning is logged if it is set). See `docs/native-vault.md`.
- The test stack registers its accounts with the KDF in `TEST_KDF` (`pbkdf2`, the default, or `argon2id`: 64 MiB, 3 iterations, parallelism 4), and `docker/bw-seed.js` and the new `docker/bw-apikey.js` log in with whatever KDF the account reports. The Python in `docker/setup-entrypoint.sh` (PBKDF2 only) is gone. `BW_CLI_VERSION` (a build argument of `docker/bw-cli.Dockerfile`, default 2026.11.0) selects the Bitwarden CLI; `scripts/dev-setup.*` build the images explicitly. A second account (`org-owner@ferrowarden.test`) owns a second organisation whose collection hides one item's password from the test account (`docker/bw-seed-hidden.js`, `tests/seed/hidden.json`).
- CI runs the whole stack a second time against **Vaultwarden 1.36.0 with an Argon2id account** and the Bitwarden CLI of its time (`docs/cicd.md`). The native backend's Argon2id unlock path has unit tests as well as that end-to-end run.

- **No Node.js, shell or openssl anywhere in the default deployment.** The `internal-certs` one-shot, the last service built from the Node-based CLI image, now runs `ferrowarden internal-certs` from the Ferrowarden image (`entrypoint: ["/app/ferrowarden", "internal-certs"]`). It runs with `network_mode: none`, a read-only root filesystem, `cap_drop: [ALL]` and `no-new-privileges`, as root (`user: "0"`) because existing `internal-pki` volumes are root-owned; with no capabilities root can still only write files it owns. The existing internal CA and certificates are kept: a CA made by the old script is reused as it is, a still-valid Vaultwarden certificate is not re-issued, and a re-issued one verifies against the old `ca.crt`. `ferrowarden` and `internal-certs` share one image (`ferrowarden:local`; `ferrowarden:test` in the test stack). `docker/gen-internal-certs.sh` is removed, and `docker/bw-cli.Dockerfile` (now only for the test setup scripts and the deprecated bw-serve) no longer installs openssl or carries the script.
- **Hardened container and deployment** (#34). The `ferrowarden` image is now a statically linked musl binary on `scratch` (about 26 MB, down from about 165 MB): no shell, no package manager, no `curl`, no libc. It contains only the binary, a minimal `/etc/passwd` and `/etc/group` for UID/GID 999, and an empty `/data` owned by that user. The build image is pinned by digest. `docker-compose.yml` and `docker-compose.test.yml` now run `ferrowarden` and `bw-serve` with `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges`, `pids_limit` and `mem_limit` (Vaultwarden gets `no-new-privileges` only, since it binds port 443 as root). `bw serve` writes only its data directory (`data.json`): a volume in production, a `tmpfs` in the test stack. Ferrowarden writes only the key file (`/data/agent_keys.json` and its `.tmp` sibling) and the optional event file, all on the `ferrowarden-keys` volume. The integration suite and the secret gate run against this hardened configuration in CI. See [Deployment Profiles](docs/deployment-profiles.md) for what it does and does not protect against.
- **Secret files are read by Ferrowarden, not an entrypoint script.** `FERROWARDEN_ADMIN_KEY_FILE` is now handled in Rust, in the same way as the notifier `*_TOKEN_FILE` variables: read into wiped memory, trailing newlines removed, an empty file refused, the same errors (including the `cannot read ... as UID 999` hint). The admin key is **never placed in the process environment**: `/proc/<pid>/environ` and `docker inspect` show only the file's path. A plain `FERROWARDEN_ADMIN_KEY` still wins if both are set. `docker/ferrowarden-entrypoint.sh` is removed. CI checks the container's `/proc/<pid>/environ` on every run.
- **The container health check is `ferrowarden healthcheck`**, a new subcommand: it reads the same settings as the server (no secrets), requests `GET /health` on the server's own port within 3 seconds, and exits 0 on HTTP 200 and 1 otherwise with one line on stderr. With TLS on it verifies the server's certificate: only the certificate in `tls_cert_file` is accepted and the peer must hold its key, so a self-signed certificate needs no `-k` and verification is never disabled. All compose files use it, including the test stack, which gains health checks for `ferrowarden` and `bw-serve`.
- The test stack's security event file moved from `/tmp/ferrowarden-events/events.jsonl` to `/data/events/events.jsonl` (a volume; the root filesystem is read-only). `scripts/check-no-secrets.sh` follows.

Error messages name the problem but never echo values from the body.

### Upgrading

- **Breaking: the native vault backend is the default and `bw-serve` is gone from the default stack.** Follow the step-by-step note at the top of **Changed** (or [docs/release-notes/v0.2.0.md](docs/release-notes/v0.2.0.md#upgrading)).
- **The Ferrowarden image has no shell.** Custom `entrypoint:` or `command:` wrappers around `/app/ferrowarden` (the entrypoint script is gone, and so is `/bin/sh`) and `docker exec ... sh` no longer work. To debug, use `docker logs`, `docker cp`, `docker compose exec ferrowarden /app/ferrowarden healthcheck`, or a temporary debug container with `--network container:<id>` or `--pid container:<id>`; see [Operations](docs/operations.md#debugging-a-container-with-no-shell).
- **Health checks that call `curl` must change** to `["CMD", "/app/ferrowarden", "healthcheck"]`: there is no `curl` in the image. This applies to your own Compose overrides and to external monitors that ran `docker exec ... curl`.
- **Everything Ferrowarden writes must be on a volume,** because the root filesystem is read-only. The default key file (`/data/agent_keys.json`) already is. If you set `FERROWARDEN_EVENTS__FILE`, use a path under `/data` (or another mounted volume), not `/tmp`. Bind mounts must be writable by UID 999, as before; files you mount read-only (secrets, certificates) must be readable by UID 999.
- **`internal-certs` now runs the Ferrowarden image.** Nothing to do if you pull the new `docker-compose.yml`: the existing CA, the certificate and the `internal-pki` and `internal-ca-public` volumes are reused as they are (restart `vaultwarden` only if a certificate was re-issued). If you maintain your own Compose file, give `internal-certs` the Ferrowarden image, `entrypoint: ["/app/ferrowarden", "internal-certs"]` and `user: "0"`, and drop the build of `docker/bw-cli.Dockerfile` for it. Misspelled or unparsable entries in `VAULTWARDEN_CERT_SANS` used to be passed to openssl as they were; they are now refused with a message that names the entry.
- If you copied `docker-compose.yml` rather than pulling it, add the hardening from the new file (`read_only`, `cap_drop`, `security_opt`, `pids_limit`, `mem_limit`) and the new health check. With `read_only: true` and no `tmpfs`, an existing deployment needs nothing else. If you raised your Vaultwarden account's Argon2 memory above 1 GiB, raise `mem_limit` for the admin UI sign-in.
- **bw-serve:** now deprecated and no longer in the default stack: see the breaking change under Changed. If you stay on it with your own Compose file, mount a volume (or a `tmpfs`) at `/home/node/.config/Bitwarden CLI`, since the read-only root filesystem leaves no other writable place for the CLI.
- **Admin UI (optional):** nothing changes unless you set `FERROWARDEN_UI__BIND`. The Docker image now needs the `templates/` directory when built from source (the `Dockerfile` copies it). Run `docker compose up -d --build` so `internal-certs` fills the new `internal-ca-public` volume. Keep the UI port off agent-reachable networks and serve it over HTTPS (see `docs/admin-ui.md`).
- **Agent keys now require an explicit policy, and keys created with 0.1.0 become deny-all.** `POST /v1/admin/keys` now requires `credentials` and `methods` (`["*"]` for everything, `[]` for nothing; omitting them or sending `null` is a `400`). Keys already in your key file have no policy: after the upgrade they authenticate but can list no credentials and forward nothing until you set one. They are shown with `"policy_set": false` in `GET /v1/admin/keys`, counted in the `startup` event (`keys_without_policy`), and a warning is logged at startup. To restore the previous behaviour for a key, run:

  ```sh
  curl -X PATCH https://<host>:3000/v1/admin/keys/<key-id> \
    -H "X-Admin-Key: $ADMIN_KEY" -H "Content-Type: application/json" \
    -d '{"credentials":["*"],"methods":["*"]}'
  ```

  (set both fields; a field you leave out stays deny-all on such a key). Better, scope each key to what its agent needs. Scripts that create keys must send a policy. A key file with `null` policy values fails to load at startup.
- **`/v1/forward` now rejects methods outside `GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS`** (for example `TRACE` or `CONNECT`) with `400`, for every key. The method is matched case-insensitively.
- **Key list output now includes policy fields** (`credentials`, `methods`, `policy_set`), and so do the create and patch responses. Unrestricted is shown as `["*"]`, never `null`.
- **`GET /v1/admin/audit` returns security events instead of the old audit entries.** The fields changed: `timestamp` is now `@timestamp`, `agent_id`/`agent_name` are `ferrowarden.key.id`/`.name`, `method` and `target_url` are `http.request.method` and `url.original`, `credential_names` is `ferrowarden.credentials`, `response_status` is `http.response.status_code` (now a number; it was the string `"Some(200)"`), and `outcome` is `event.outcome` (`success`/`failure`) with the cause in `event.reason`. The ring buffer now also contains non-forward events (authentication failures, key changes, vault events), so filter on `event.action == "forward"` for the old view.
- **The `audit` log line is gone.** The `tracing` line with `message: "audit"` (fields `agent_id`, `credential_names`, `outcome`, ...) is replaced by security events on stdout with a different shape (`event.dataset == "ferrowarden.security"`). Update Loki queries and Wazuh decoders that matched `message="audit"`; see `docs/events.md` and `docs/logging.md`.
- **Authentication is now checked before request bodies are parsed.** An unauthenticated request with a malformed body gets `401` (it used to get a `400` with parse details). Authenticated requests are unaffected.
- **The `api_prefix` value is no longer written to the startup log.** The startup log says only that a prefix is configured.
- **Ferrowarden now shuts down gracefully** on SIGTERM and Ctrl-C (in-flight requests get up to 10 seconds) and flushes the event sinks before exiting.
- **Items with master password re-prompt are now refused (`403`).** Previously they were usable. Turn re-prompt off on items agents should use.
- **URIs with match type *regex* or *never* no longer act as host bindings.** Add a normal URI (or a `ferrowarden_uris` field) if a credential relied on one.
- **Stricter request parsing.** Requests with unknown fields, duplicate JSON keys, case-insensitively duplicated header names, or unknown/repeated query parameters on `/v1/credentials` now get `400`. A key file with duplicate keys or unknown fields fails to load at startup.

## [0.1.0] — 2026-11-21 (preview)

First public release. Ferrowarden is a credential proxy for AI agents: credentials live in a self-hosted Vaultwarden password manager, agents call APIs through Ferrowarden with `{{vault:name}}` placeholders, and credential values are kept out of the agent's context by design.

### Added

- **Credential proxy** — `POST /v1/forward` substitutes `{{vault:name}}` placeholders in the URL path/query, headers and JSON or raw-string bodies, forwards the request, and returns the scrubbed response. `GET /v1/credentials` lists credential names, never values.
- **Credential host binding** — each credential is only sent to the hosts listed in its Vaultwarden item's URIs (`enforce_credential_hosts`, on by default). Placeholders cannot change the target scheme, host or port.
- **Outbound target policy** — enforced at DNS resolution: bw serve is always refused; private, loopback, link-local (cloud metadata) and other internal addresses need `allowed_targets` or `allow_private_targets`.
- **Response scrubbing** — every substituted value is removed from response bodies, headers and errors in raw, JSON-escaped, URL-encoded and base64 forms, plus common credential patterns. Binary responses are returned base64-encoded.
- **Agent and admin keys** — agent keys stored only as SHA-256 hashes (optionally persisted); environment-only admin key (≥ 32 characters); key rotation via the admin API.
- **Audit log** — credential names (never values), target, outcome and status for every request, in memory and as structured JSON log lines.
- **Rate limiting** — per client IP (configurable: `agent_rate_limit_*` and `admin_rate_limit_*`), with `trusted_proxies` for deployments behind a reverse proxy.
- **Vault lifecycle** — file or manual unlock; periodic `bw serve` sync and credential refresh (`refresh_interval_secs`); automatic re-unlock in file mode after bw serve restarts — immediately when a request finds the vault locked (the request is retried once), otherwise on the next refresh.
- **Configurable API prefix** — `api_prefix` moves every route except `/health` under a hard-to-guess path.
- **Docker Compose stack** — Vaultwarden (pinned 1.37.5) with its web vault published for managing credentials; Bitwarden CLI 2026.11.0 `bw serve` on an internal-only network; internal CA and HTTPS between bw serve and Vaultwarden; settings via `.env` (see `.env.example`).
- **Native TLS** for the agent API (rustls), or run behind a TLS reverse proxy such as Pangolin.
- **Test stack and tooling** — one-command dev setup (`scripts/dev-setup.sh` / `.ps1`), mock API, integration tests covering the leak-prevention guarantees, and a Claude Code skill (`.claude/skills/ferrowarden`).

### Upgrading from pre-release snapshots

- **Vault items need URIs.** A credential whose Vaultwarden item has no URIs, or whose URIs don't match the target host, is now refused with `403`. Add the service's URL to each item.
- **Internal targets need `allowed_targets`.** Services on private networks (e.g. `192.168.1.0/24`, `proxmox.lan`) are blocked until listed.
- **Vaultwarden now uses HTTPS on the internal network** (`https://vaultwarden`), required by current Bitwarden CLI releases. The `internal-certs` service creates the certificates; existing `bw-data` volumes are logged out and reconfigured automatically.
- **Linux hosts:** the Ferrowarden container runs as UID 999 and bw serve as UID 1000; secret files and `certs/server.key` must be readable by them (see `docs/setup.md`).
- **`/v1/unlock`** now accepts `X-Admin-Key` (as documented) and shares the admin rate limit; `Authorization: Bearer` still works.
- **Forward responses** include a new `body_encoding` field (`"utf8"` or `"base64"`).
